# 供应商连接调度验收

状态：已进入测试先行实现，部分用例已有可执行证据。日期：2026-10-16。规则与接口以 [供应商连接调度策略](./provider-routing-strategies.md) 为准；实际命令、结果、实现边界见 [实现与验证记录](./provider-routing-verification.md)。本文 accepted 表示“本规格明确纳入”，分组中的 planned 保留为完整验收目标，不能因为局部测试通过而批量改成 passed。

## 1. 验收方法

- 单位与时间使用合成数据，不读取用户真实凭据，不调用真实供应商生成内容。
- 规则层提供可控 clock、只读快照、确定性请求估计和稳定 ID；并发层使用 deferred/barrier 控制 reserve、dispatch、响应、quota 读取与取消顺序，不用 sleep 掩盖竞态。
- 集成层使用当前本地 HTTP/worker/CLI fixtures；网络计数以模拟上游实际收到的 POST 为证据，不以 mock 函数调用数代替物理尝试。
- 金额、Token、厂商 Credits、比例、窗口和请求数分别断言。estimated/unknown 不能进入 actual 断言或用量账本冒充事实。
- 每个用例记录 owner/策略/版本、输入快照与事件顺序、选择/排除理由、真实请求次数、预留/终态状态和清理结果。UI 用例另保留截图、交互步骤与服务提交记录。
- 同一不变量在三个模型协议中选取代表性用例验证；协议转换、归因、取消和流终态必须覆盖三协议，不能以全部排列数量冒充有效覆盖。

## 2. 范围与裁剪

| 维度     | 纳入等价类                                                                             | 裁剪/理由                                                            |
| -------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 策略     | 五个新稳定值、legacy、显式 fallback                                                    | 不接受 Magpie 名称作为当前仓库已有配置。                             |
| owner    | 同一 OAuth Host、原 API CLI runtime、独立 Server、已授权远端 attachment                | 跨 owner 全局原子额度不在首期保证范围。                              |
| 客户端   | desktop-continuous、web-remote-replayable                                              | 两者 UI 恢复语义分开，真实业务 owner 相同。                          |
| 额度     | 数值已知、比例已知、unknown/stale/partial/unsupported、共享/独立、fixed/rolling/expiry | 不枚举无业务差异的任意厂商名称；用真实适配器 fixtures 验证语义映射。 |
| 请求     | 小/大、工具继续、新轮、并行子代理、non-turn、取消、输出前/后失败                       | 不创建第二个 accepted 队列模拟未来工作。                             |
| 缓存     | 无上报、有效五分钟/一小时事实、未知 TTL、命中/miss、不可移植绑定                       | 不按供应商品牌默认推断价格、TTL 或可移植性。                         |
| 身份     | workspace identity fallback、同路径不同 identity、remoteSessionId、actor/epoch 换代    | 不根据路径相同合并远程请求。                                         |
| 后续能力 | 跨供应商模型组、嵌套组、第三方策略、自动兑换重置券                                     | pruned：未授权为本期实现；原 Runtime 模型接管只保留边界回归。        |

## 10. 三个详细并发场景

### A. 同一额度池的两账号竞争

Setup：原 OAuth owner 下 A/B 共用组织窗口 W，remaining=100，coverage 已验证，无其它本地消耗；每个请求对 W 的可信需求上界为 60；两个账号都有空闲槽。

1. 请求 R1/R2 在同一 barrier 后执行只读 plan，两者可以都看到 100。
2. 原 owner 先接受 R1 的原子 reserve，W 预留 60，剩余安全下界 40。
3. R2 的旧 plan 在 reserve 阶段冲突，重新读取 W=40；换成 B 仍关联同一个 W，不能绕过限制。
4. R1 物理完成且实际消耗 40；在没有新快照且原余额覆盖已知时，从预留 60 换成待对账实际 40，安全可用为 60。
5. R2 可以新 reserve 60；幂等重放 R1 终态不再多释放 20，也不把 R2 的在途预留清掉。

证据：两个租约的窗口 key 相同、每个时刻资源快照、实际上游 POST 顺序、原 budget permit、终态去重键和最终在途槽为零。

### B. 新额度读数不能抹掉读取期间的消耗

Setup：W 原 remaining=100，seq 11 派发，估计 40；原额度 owner 开始读取；seq 11 实际完成用量 30，新读数返回 remaining=70。

1. 新读数明确 coversThroughSeq=11：移除已结算的 30 增量；安全余额 70，不再重复减至 40。
2. 新读数 coverage unverified：保留 30 增量，保守下界可为 40，标 conservative；不得伪装成真实余额 40 或精确余额 70。
3. 两个顺序都覆盖：读数先于 usage、usage 先于读数。pending 实际与预留只能替换同一笔状态，不允许同时扣完整估计与完整实际。
4. 加入 seq 12 在途 20：即使 seq 11 已覆盖，20 的在途预留依然存在。

证据：readingRevision、覆盖证明来源、窗口实例、每笔增量来源和 UI 质量标记。只比较 checkedAt 大小不构成通过。

### C. 取消、物理收尾和迟到用量

Setup：请求在 A 上已 dispatch；上游正在输出；caller 取消，driver 清理被 deferred 保留，usage 仍未到达。

1. caller 立即结束业务等待；新的 actor 不得复用原 attempt 重发。
2. 原 owner 保留物理 completion 与在途槽，直到 driver/reader 真实收尾；票据 TTL 不释放槽。
3. 物理收尾完成时释放并发槽，但未知消费估计仍待对账。
4. 后到 actual usage 只更新原 attempt 消费；重复反馈不重复扣；如果 A 已重新授权换 epoch，旧反馈不能影响新身份调度。
5. 原 usage ledger 仍可按原已冻结身份处理历史事实，不因调度 owner 已关闭就把旧用量归到新账号。

证据：caller/physicalEnded/usage 三个不同终点、原取消传播、zero second POST、completion retain 与原账本归因。
